# Latency on the Dublin VPS, 2026-09-24

Measured, fixed, and measured again. The same strategy (`spot_lag`, paper,
`venue_lag` scenario) ran on the old and the new code side by side on this machine.

## Where the time went

| stage | before | after | how measured |
|---|---:|---:|---|
| Binance trade to this VPS (network) | ~125 ms | same | standalone listener, `@trade` and `@aggTrade` identical |
| Coinbase / Bybit to this VPS (network) | 51 / 98 ms | same | standalone listener |
| **inside the bot, before a message is read** | **150-280 ms, spikes to seconds** | **p50 1 ms, p99 17-24 ms** | new `loop_lag_ms` monitor; same-minute comparison |
| bot's reported spot lag (Binance, p50) | 270-540 ms, spikes 1.8-9.2 s | 160-182 ms | STATUS lines, same 5 minutes |
| bot CPU | 67 % of a core | 28 % | py-spy, same 30 s, both bots |
| order: decision to worker pickup | up to 50 ms | ~0 | worker woken on submit |
| order: POST on a cold connection | ~107 ms | ~27 ms (kept warm) | curl to clob.polymarket.com (Cloudflare DUB edge, 2 ms) |
| order signing | 14-25 ms | same | forensics `sign_ms` |

## What was wrong, what changed

1. **The dashboard state froze the event loop.** `data/live_state.json` was
   rewritten 2-4 times a second and had grown to 5.1 MB, 99.8 % of it
   `price_history`. `orjson.dumps` took 56 ms and holds the GIL, so running it
   in a thread did not help: 41 % of the bot's busy CPU, and every spot and book
   message waited behind it. Chart points now go to per-market append-only files
   (`history_store.py`, `data/live_state.history/<slug>.jsonl`). The state is
   ~11-18 KB and carries `history_meta` (the counts). The dashboard server
   reads the one market it draws. Slugs are validated before any path is built.
2. **A backlogged feed was treated as fresh.** Binance's quote stream is ~1,480
   msg/s (~210 KB/s) over a 235 ms route to Tokyo, and TCP (CUBIC) falls behind
   after packet loss. Binance was measured 9.8 s behind while Bybit and Coinbase
   were 0.1 s. Quotes carry no timestamp, so they entered the median, and the
   cross-exchange basis, as if they were new. Every feed's own trade timestamps
   now measure its lag. An exchange more than 750 ms behind leaves the composite
   (and the basis) until it is back under 400 ms. A connection more than 5 s
   behind for 3 s is reconnected.
3. **Order path.** The worker polled every 50 ms and now wakes on submit. The
   SDK closes idle connections at 30 s, so every order paid a new TLS handshake;
   a `/time` GET every 15 s while idle keeps the connection warm.
4. **Duplicate work.** Order-flow features are memoised on (time, data version):
   a hit is the same answer, and any new trade or quote recomputes. The dashboard's
   `twap60` reuses the value `_tick` computed. The TWAP integral skips samples
   before its window, and the latency report is cached for 1 s (orders clear the
   cache). Tests prove the TWAP and order-flow results are bit-identical to the
   old code.
5. **Measurement.** Per-exchange lag (`spot_p50_<exchange>` in
   `measured_latency_ms`), `loop_lag_ms`, `lagging_feeds`, and a loop-lag field
   on the STATUS line. The feeds parse with orjson.

Tests: `tests/test_latency_optimizations.py`.

## Event-driven spot-lag decisions (`TPB_SPOT_LAG_EVENT_DRIVEN=1`, off by default)

On the 90-minute tick recording (1,295 shocks of at least 3σ in 1 s), the token's
median 5 s response was 10c. About half of it was done when the shock reached this
machine. What was left: 4.5-5c at detection, 3c 100 ms later, 2c 200 ms later.
Coinbase arrives first on the network but moves later. On this machine's clock
Binance saw the shock first in 40 % of events, Bybit 38 %, Coinbase 22 %. The
composite median is 30 ms behind the first, so no source switch.

The bot waited for its spot model (a 100 ms throttle) and then for its 200 ms
decision tick. `SpotHistory` kept one point per 200 ms, so "the price now" could be
200 ms old. Now:
* a quote whose 1 s move is at least 0.9 × k_sigma updates the model at once and
  evaluates that asset's markets at once (`LiveBot._maybe_shock_eval`), at most
  once per asset per 50 ms. The tick path's gates, revalidation, kill switch and
  pre-send checklist all apply (`_evaluate_entries`);
* `SpotHistory` answers "now" with the newest price (the stored samples are unchanged).

A/B on live data, two isolated paper bots on identical code, 15 minutes. Age of the
newest exchange trade when the engine first saw each shock (`shock_decision_age_ms`):

| | shocks | p25 | median | p75 | p90 |
|---|---:|---:|---:|---:|---:|
| tick (flag off) | 36 | 181 ms | 225 ms | 314 ms | 445 ms |
| event-driven (flag on) | 45 | 119 ms | 148 ms | 252 ms | 350 ms |

Both bots saw the same BTC shock in the same second. The tick bot capped its order at
0.55 and the event bot at 0.49, which is the earlier price. Both were killed in the
paper venue-lag scenario. Four orders are not evidence of profit. The flag makes the
strategy see shocks sooner; whether that turns into fills and P&L has to be measured
in paper before it goes near the live bot.

## Not changed, and why

* **Which exchange drives the price.** Coinbase arrives ~75 ms before Binance
  here, but switching the composite changes trading, not just speed. Whether
  Coinbase leads these markets is a question for `scripts/spot_lag_ticks.py`.
* **Orders queue behind reconcile / redeem in the one worker.** Running them
  concurrently would mean two threads mutating the real-money position state.
* **Kernel TCP (BBR instead of CUBIC).** It would help the long Binance route,
  but it is a system-wide setting for every process on the VPS; the operator's call.
* **Moving the VPS.** Polymarket is 2 ms away. From Tokyo, every order would
  cross the long route instead of the market data.

## Deploying

A running bot keeps its old code until it restarts. Restart the dashboard
(`tpb-web`) together with the bots: the new bot's state has no `price_history`,
and only the new server knows where to find the chart points. The new server
still reads an old bot's state.
