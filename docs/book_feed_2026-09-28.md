# Book feed: speed and fill rate (2026-09-28)

**Why.** On the 09-26 real-money run (242 orders) the fill rate depended almost entirely on how fresh the
Polymarket book was when the bot decided: 26% of orders filled when the book was under 60 ms old, 4% at
60–120 ms, none above 120 ms. Spot latency and the venue round trip made no difference. The book feed itself
was the problem: 1,477 connections in 46 hours (about every 2 minutes), because every newly registered
market forced a reconnect, and each reconnect made the venue send 42 full snapshots at once, which is the
burst that produces "1013 slow consumer" drops (about 190 a day) and a gap in the books. Drops also
clustered in the first 30 s of each window, when seven ~500 KB archive files were serialised inside the
feed's event loop.

**What changed** (`live.py`, tests in `tests/test_book_feed_handover.py`):

1. **One resubscribe per discovery pass**, not one per market (`discover`), plus a 0.5 s debounce.
2. **Connect before close.** `polymarket_feed` is now a supervisor: on a resubscribe it opens the next
   connection, keeps reading the current one until the new one has delivered a snapshot for every token (or
   6 s), then retires the old one. Both connections count as current during the handover
   (`_book_conns_ok`), so no book goes stale and the strategy never sees a gap. A dropped connection is
   replaced the same way with the usual backoff; a planned handover is not counted as a drop.
3. **Archive writes off the loop.** The closed window's record is snapshotted on the loop and serialised
   with orjson in a worker thread (`_chart_doc` / `_write_chart_doc`).
4. **Bounded books.** `LiveBook` keeps the best 40 levels per side (the strategy reads the touch, the depth
   within two ticks and one order's walk). No sorted-view cache, because tests and tools assign the level
   dicts directly.
5. **Subscription skip list.** `TPB_BOOK_SKIP_ASSETS` (comma list) keeps an asset's markets tracked but off
   the websocket; the live app sets `HYPE`, which the strategy excludes: 36 tokens instead of 42.
6. **Measurement.** The STATUS line shows `book conn N drops M`.
7. **Less competition.** `tpb-spotlag-paper-ma74` was stopped (its paper fills were shown to be inflated
   anyway); the live bot is the only spot-lag process.

**What to look for after the restart:** connections per hour (was ~32; expect 12, one per window), drops
per day (was ~190; expect near 0), book latency median under 60 ms and p90 under 120 ms on the STATUS line,
and the fill rate moving from 8–12% toward the 20–25% that fresh-book orders already achieve.

**Not done:** a separate feed process (the robust version of item 2), and moving the machine nearer the
venue (round trip 219 ms median), which is likely the largest remaining lever.

## Order points on the chart (same day)

The price chart already drew every signal decision (circles at the ask) and every buy (◆). It now also
draws every ORDER the bot sent, at its limit price: **×** an order killed at the venue (the ask was gone, the
cap refused it, it expired), **□** an order still in flight, **◇** an exit that sold (at its fill price).
Hover gives the limit, size, fill price, the reason and how long the venue took. Data: `DecisionJournal`
keeps up to 60 order marks per market (`order_marks_for`), the snapshot carries `order_marks`, the server
trims it to the selected chart like `signal_marks`, and exported PNGs include the marks. Tests:
`tests/test_order_marks.py`. The marks exist only for bots running this code (restart to see them).
