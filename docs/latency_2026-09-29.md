# Order latency: where the time goes and what our code can remove (2026-09-29)

**Answer.** The network is not the problem: Polymarket sits behind Cloudflare's Dublin edge, 0.8 ms from this
VPS. The bot loses ~100 ms per order, and 300–700 ms when several markets fire together, in its own code.
Three fixes are implemented; two need a restart of the live bot to take effect.

## Measured (422 real orders, 09-26 → 09-29; medians unless marked)

| stage | time | cause |
|---|---:|---|
| exchange trade → spot received | 121 ms | distance to the exchanges (Coinbase 73 ms, Bybit 120, Binance 152 from Dublin) |
| **wait for the next decision tick** | **~90 ms** (spot age at decision 209 ms) | **our code**: decisions run on a 200 ms timer |
| signing | 15 ms | **our code**: pure-Python elliptic-curve backend |
| **wait in the order worker** | **20 ms; 296 ms median, 684 ms p90 when orders are decided together** | **our code**: one worker, serial POSTs, shared with reconciles and redemptions |
| POST → venue reply | 226 ms (p90 447) | Polymarket's order processing: a warm request to the same host takes ~25 ms, a new TLS connection ~100 ms |

It matters: orders sent within 40 ms of the decision filled 11%; 40–100 ms, 5%; over 100 ms, almost none.

## What changed

1. **Fast signing.** `coincurve` installed (and added to the `live` extras). `eth_keys` switches to it
   automatically: 0.83 ms per signature instead of 8.6 ms, verified byte-identical on 200 signatures with a
   throwaway key. Active in any process started after 2026-09-29 14:30 UTC.
2. **Order lanes** (`TPB_LIVE_ORDER_LANES`, default 0 = unchanged). N dedicated threads take fill-or-kill
   orders straight from `submit()` and sign and POST them in parallel over the SDK's shared HTTP/2
   connection; reconciles, redemptions and keep-alives stay on the old worker. Safeguards:
   - **exposure**: an entry reserves its worst-case notional atomically before posting, so parallel entries
     cannot all pass the $24 cap;
   - **guards**: a reconcile, position check or foreign-trade check that overlaps any POST is discarded and
     retried 2 s later, so a fill whose reply is still in flight can never latch BALANCE_DRIFT,
     UNKNOWN_POSITION or FOREIGN_TRADE (09-26's 29-hour latch was this class of problem);
   - **results**: `step()` now pops finished orders one by one instead of copy-then-clear, which could
     silently drop a result appended in between. That race existed in the original single-worker design too
     and is fixed for both;
   - a lane that hits an unexpected error books it as an API error and keeps running.
   Tests: `tests/test_order_lanes.py` (6), plus the existing adapter tests. Simulation of the live situation
   (a 15 ms decision tick, a 220 ms venue): decision → POST start 15.7 → 5.6 ms for one order;
   302 ms median / 550 ms p90 → 6 ms / 16 ms for four at once.
3. **Event-driven decisions** (`TPB_SPOT_LAG_EVENT_DRIVEN=1`, already built and paper-run since 09-24):
   evaluate the moment a spot quote shows a shock instead of on the 200 ms timer. Paper evidence: shock
   decision age 225 → 148 ms median (docs/latency_2026-09-24.md); spot age at decision 201 → 154 ms against
   the tick-driven paper bot over the same hours (docs/spot_lag_paper_history_2026-09-25.md).

## Expected effect on the live bot

- Spot receipt → POST start: ~125 ms → ~25–40 ms for a single order; ~400–700 ms → ~30 ms for the orders of a
  market-wide shock, which are often the best opportunities.
- Not changed: the exchanges' distance (~120 ms) and Polymarket's own POST processing (~200 ms).

## To enable (live bot, real money: a restart)

In `ecosystem.spotlag.config.js`, `tpb-spotlag-live` env: `TPB_LIVE_ORDER_LANES: '4'` and
`TPB_SPOT_LAG_EVENT_DRIVEN: '1'`, then `pm2 delete tpb-spotlag-live && pm2 start ecosystem.spotlag.config.js
--only tpb-spotlag-live`. Afterwards compare `presend_ms` and `spot_age_ms` in `data/trade_forensics.jsonl`
against the table above.
